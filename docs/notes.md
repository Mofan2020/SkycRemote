# 开发笔记

记的是决定和原因，不是过程流水账。

## 界面和命令行是两个程序，不是一个程序的两副面孔

以前 `skycremote` 是个命令行程序，`skycremote ui` 才开窗口。听着省事，
其实两头不讨好：想开界面得先记一条子命令，想在终端里干活又得跟一整套
界面挤在一个二进制里。

现在拆成两个：

- `skycremote` —— 窗口。启动就是它，没有参数。
- `skycremote-cli` —— 命令行工具。装进 PATH 的是它。

拆开的另一个理由是 macOS 的应用包：`Contents/MacOS/` 里放两个程序，
窗口是 `SkycRemote`，工具是 `skycremote-cli`。窗口启动时把工具复制到
PATH 里的目录，两件事一次装完。

## 命令行工具装进 PATH 的时候不问管理员密码

自己弹密码框的程序，是用户会直接关掉的程序。所以候选目录按「写得进去」
的可能性排序，第一个能写的就用：

- macOS：`/usr/local/bin` → `/opt/homebrew/bin` → `~/.local/bin`
- Windows：安装目录下的 `cli` 文件夹，用户自己的 PATH

最后一个用 `~/.local/bin` 的要额外往 `~/.zshrc` 里加一行 PATH，因为那个
目录默认不在 PATH 上。这行只在不在的时候才加，程序起两次不会把文件越写越长。

**只从装好的位置装**。开发时在 `target/release` 里跑起来的程序不会去动
PATH：macOS 上看路径里有没有 `.app/Contents/MacOS`，Windows 上看旁边有没有
`cli` 文件夹。开发构建不是这台机器该有的东西。

## Windows 的安装程序是自己写的

不用 NSIS。安装程序是 `skycremote-installer` 这个 crate 里的一个程序，
要装的文件在编译时折进它里面（`include_dir` + `build.rs`），安装的时候
自己写文件、自己写注册表、自己做快捷方式。

三件事值得记：

- **装给用户，不装给机器**。注册表写的是 `HKEY_CURRENT_USER`，所以不需要
  管理员密码，也装不到别的账户上 —— 这个程序只跟它自己所在的机器说话。
- **卸载是复制出去再删**。Windows 不让一个正在运行的程序删掉自己，
  所以卸载程序先把自己复制到临时目录，让那份去删安装目录。
- **PATH 改了要通知**。写完注册表要发一条 `WM_SETTINGCHANGE`，否则已经开着的
  终端还拿着旧的 PATH。

## 共享是一个可以被取消的服务

共享端原来是个死循环：开始等对面，然后一直等着，停不下来。现在是
`host::HostService`：它拿着一个取消令牌，等对面的时候看令牌，进了会话
之后也看令牌。窗口点「停止共享」就是取消令牌。

等待那一段原来是同步阻塞的（`punch_wait` 在 socket 上带超时地读），
所以加了一个能看取消令牌的变体。令牌最多让等待多花一个读超时的时间，
这在人看来就是「立刻」。

## 碰真实屏幕的测试默认不跑

macOS 上问系统要屏幕，系统会先问人一句。测试跑到那里，用户的屏幕上就
多一个对话框，等着他回答。测试套件打扰跑它的人，人就会把测试跳过 ——
于是那个测试就永远没人跑了。

所以碰屏幕的三个测试改成了显式开关：`SKYCREMOTE_CAPTURE_TESTS=1` 才跑，
默认跳过，并且会打印一句「为什么跳过」，不留成静默的洞。

这条不是只关于屏幕：任何会在用户屏幕上弹东西、或者拿走用户屏幕和麦克风
内容的步骤，都不该在默认路径上。

## 屏幕尺寸的换算放在数据里，不放在 cfg 里

三平台的采集后端报的尺寸单位不一样：macOS 和 Linux 报的是逻辑单位
（点），要乘缩放系数才是像素；Windows 的 `dmPelsWidth` 已经是物理像素，
再乘一次就会把 4K 屏说成 7680 宽。

这个差异一开始写成 `#[cfg(target_os = "windows")]`，结果在 macOS 上跑
Windows 的测试时，测的是 macOS 的分支 —— Windows 的数字根本测不到。
`cfg` 描述的是「代码跑在哪台机器上」，而这里要说的是「这个后端报的是
什么单位」，两件事。

所以改成平台模块各自声明 `SIZE_IS_PIXELS`，`make_screen` 看数据决定
乘不乘。这样在任何机器上都能验各平台的数字。

参数也从八个散装参数收进了 `ScreenSpec`：这八个字段永远一起出现，
它们是「一块屏幕的描述」，不是八个无关的数。

## Linux 上编译要装的东西

`tao`/`wry` 要 GTK 和 WebKitGTK，`xcap` 要 PipeWire，`webkit2gtk` 链接
时还要 Mesa 的 GBM。清单写在 `.github/workflows/ci.yml` 的 `LINUX_DEPS`
里，两个 job 共用一份 —— 同一份清单写两遍，漏的总是没人看的那一份。

这份清单是四轮试出来的，每一轮 GitHub 上只报一行：

| 缺的 | 报的错 |
|---|---|
| GTK / GLib | `Package glib-2.0 was not found` |
| PipeWire | `Package libpipewire-0.3 was not found` |
| GBM | `rust-lld: error: unable to find library -lgbm` |
| libclang | `Unable to find libclang`（bindgen 生成 pipewire 绑定时） |

前两轮是 pkg-config 找不到，第三轮是链接器找不到，第四轮是 bindgen
找不到 —— 一个比一个晚炸，所以一轮白等一次 CI。

**验证的地方**：本机有 OrbStack 的 Linux 机器 `ServerForTest`
（Ubuntu 26.04，arm64，192.168.139.149），`orb -m ServerForTest <命令>`
就能进去跑。比在 CI 上试快得多，也不占 GitHub 的 runner。

代码怎么进去：`orbctl push` 只认 `~/OrbStack/<机器名>/home/<用户>/`
这个路径，而且 macOS 的扩展属性会挡住 `cp`，要加 `-X`：

```
tar czf /tmp/src.tar.gz --exclude=target --exclude=.git <要传的东西>
cp -X /tmp/src.tar.gz ~/OrbStack/ServerForTest/home/skyc8266/
orb -m ServerForTest tar xzf ~/src.tar.gz -C ~/项目目录
```

SSH 直连那台机器不通（`connect to host 192.168.139.149 port 22:
Operation timed out`），走 `orb` 才进得去。

## 无显示器的 Linux 机器上，报错要说人话

在一台没有 X11 也没有 Wayland 的机器上（服务器、容器、SSH 会话），
`list_screens()` 会把 X11 客户端库的一句内部消息原样抛出来：

```
the capture backend failed: Connection closed, error during parsing display string
```

用户看到的是「连接关闭」，不知道该做什么 —— 重试多少次都没用，因为
根本不是可重试的故障。

`linux::explain_error` 现在认得这类错，返回 `Unsupported{platform: "X11"}`
并说清楚「这台机器没有显示服务器可采集，需要登录到机器自己的桌面」。
X11 客户端库有好几种说法（display string 解析失败、屏幕上没有匹配的
screen、XOpenDisplay 失败、I/O 错误），全都认。

原有的 `CaptureError::Backend` 注释写着「这个值得重试」，所以这个错误
放进去本身就是错的 —— 它不是重试能解决的，是环境问题。

这个 bug 是**在 Linux 虚拟机上跑测试才发现的**：macOS 和 Windows 上
永远碰不到，所以 CI 里只有 Linux job 能抓到它。

## workflow 自己也要被检查

一个解析不了的 workflow 不会大声失败：GitHub 直接拒绝那个文件，run
回来零个 job，日志只有一句 `failed to get run log: log not found`，
什么错都没说。

所以 CI 里加了一条 actionlint。几点：

- actionlint 不是 GitHub Action，是个 Go 工具加 pre-commit hook，官方
  仓库里没有 `action.yml`，`uses:` 引用不了
- 它的下载脚本是 bash，Windows runner 里的 bash 跟 Linux 的不是一回事，
  管道进去会挂。所以这一步只在 Linux 上跑 —— 检查的是 workflow 结构，
  跟平台无关
- 本机装了 `actionlint`（`brew install actionlint`），改完 workflow
  本地先跑一遍再推

引用同一个仓库的 workflow 要用相对路径 `./` 开头，写成完整仓库名
GitHub 会拒绝。

## 发版

tag push 触发。`check-version` 先看 tag 上的版本号和各个 crate 写的
版本号一不一致，不一致直接拦住 —— 不然发出去的包报的是错的版本号。

二进制不在发版 workflow 里重新构建，而是调用 CI 那个 workflow：
依赖清单和构建步骤只有一份，测试跑在前面，发出去的包一定是过了测试
的构建。

`release-notes.md` 就是 release 的正文。

## webview 是窗口的孩子，得有人告诉它多大

wry 的 `build_as_child` 不传尺寸的时候，webview 是 **200 × 200** —— 它就诞生在
那个尺寸上。窗口是 1280 × 820，于是页面缩在左上角一小块里，剩下的全是空的。
看起来像「界面只显示了一角」，其实是两件事：webview 没长大，而且窗口一变
尺寸它也不跟着变。

所以有两步，缺一不可：

```rust
let scale_factor = window.scale_factor();
let inner_size = window.inner_size().to_logical::<f64>(scale_factor);
let builder = WebViewBuilder::new().with_bounds(wry::Rect {
    position: tao::dpi::LogicalPosition::new(0.0, 0.0).into(),
    size: inner_size.into(),
});
```

以及在事件循环里，窗口每次改变大小都要重新告诉它：

```rust
if let Event::WindowEvent { event: WindowEvent::Resized(size), .. } = event {
    let size = size.to_logical::<f64>(scale_factor);
    let _ = webview.set_bounds(wry::Rect {
        position: tao::dpi::LogicalPosition::new(0.0, 0.0).into(),
        size: size.into(),
    });
}
```

主程序和安装程序都用了 `build_as_child`，所以两处都得写。

## 只在 Windows 上编的代码，要用 Windows 目标查一遍

装程序那一坨代码（注册表、快捷方式、PATH）全在 `cfg(target_os = "windows")` 里。
在 macOS 上 `cargo clippy` 根本不看这些代码，所以本地是绿的，CI 的 Windows
runner 是红的 —— 第一次发 v0.3.0 就是这么挂的：`never_loop`、
`chunks_exact_to_as_chunks`、`while_let_loop` 三个 lint，全在 Windows 那一侧。

能本地查出来：

```
cargo clippy --target x86_64-pc-windows-msvc -p skycremote-installer --all-targets -- -D warnings
```

这个目标装了就能查，不需要 Windows 机器。只有 `ring` 那种带 C 代码的依赖
编不过（缺 Windows 的头文件），纯 Rust 的 crate 查得了。

**新写平台专属的代码，第一件事就是拿那个目标查一遍**，别等 CI 告诉你。

## 输入注入：两个「看着绿、实际打不出字」的坑

这两条都只有真机探针能发现，单元测试 mock 掉 Xlib 之后永远看不到。Xvfb 上
的探针在 `~/injector-probe`（不在仓库里），做法是选中根窗口的按键事件、把焦点
钉到根窗口，然后调 `input::inject`，打印客户端处理事件时 `XKeycodeToKeysym`
读到的键符。

**一、`XChangeKeyboardMapping` 的返回值不是结论。** Xvfb 上它返回 0，键位表
却真的改了。按返回值判，一台能打字的机器会被判成不能打字，打中文直接报错退出。
判据只能是写完 `XSync` 之后用 `XGetKeyboardMapping` 读回来比对，读完 `XFree`。

**二、事件到达不等于字符正确。** X 的 `KeyPress` 只带 keycode，客户端必须
在处理事件的那一刻查键位表才能拿到字符。所以「借用空键位 → 改键符 → 按/松 →
立刻还原」这个流程打不出字：事件到了，客户端读到的是空键符。借用期间不许还，
统一在 `Drop` 里还。空键位（keycode 8/9 之类）通常没有对应物理键，整个会话
留着一个字符基本无害。

探针的判据要落在**字符内容**上（读到的 keysym 是不是 `0x1004e2d`），只看
「收到几个 KeyPress」会全绿。

## 守卫测试不能假定换行符

读源码做守卫的测试用 `include_str!`，在 Windows runner 上检出后是 CRLF，按
`"\n}\n"` 找代码块边界会找不到、直接 panic —— 本机是 LF 所以绿的，CI 上红。
读进来先 `.replace("\r\n", "\n")` 再断言。

## 滚轮：一个刻度滚了一百格

控制端把浏览器的 `deltaY` 原样发出去。Chrome 一个滚轮刻度给 ±100（像素），
协议里那两个字段的注释写的是「转了多少」，没有单位；接收端当成「格」用：

- Windows `wheel_steps(100)` = 100 格，再乘 `WHEEL_DELTA` 120，等于一个刻度
  滚 100 个刻度；
- X11 一个刻度按 100 次按钮 4/5；
- macOS 按「行」算，一个刻度滚 100 行。

三个平台全错，而且方向一致地快了两个数量级。

**协议里的单位改成像素**（`Scroll` 的 `dx` / `dy`），下游各自在最后一刻换算：
Windows 和 X11 只能按整格滚，用 `take_notches(余量, 像素)` 把零头留到下一次；
macOS 换成 `SCROLL_UNITS_PIXEL`，直接按像素投，手感和本机一致。控制端要先把
`deltaMode` 归一化 —— Firefox 默认给的是「行」，不换算的话滚起来像没反应。

零头必须留：轻轻滚一下只有几十像素，直接截断成 0 格，慢慢滚就完全不动。

这条只有真机能确认手感。机器上验到的是「一个刻度恰好一格」这个换算关系，
以及零头会累积到出格；实际滚动的速度、加速度、不同桌面环境的差异都还没试。



## WebView2 的数据目录不能放在程序旁边

Windows 上把程序装进 `C:\Program Files` 之后启动，窗口开不出来，报
`WebView2 error: WindowsError(0x80070005) 拒绝访问`。

原因是 WebView2 默认把自己的用户数据放在**可执行文件旁边**，也就是
`C:\Program Files\SkycRemote`。普通用户在那里没有写权限，WebView2 建不出
自己的缓存目录就直接报「拒绝访问」—— 报的是 WebView2 的错，不是 wry 的错，
所以只看「WebView2 error」很难想到是权限。

修法是把数据目录显式指到用户自己的地方：
`%LOCALAPPDATA%\SkycRemote\WebView`（安装程序用同办法的 `SetupWebView`）。
用 `wry::WebContext::new(Some(path))` + `WebViewBuilder::new_with_web_context`。

WebContext 是被 builder 借走的（`&'a mut WebContext`），所以它必须活得比
webview 长：声明顺序放在前面，让它最后被 drop。窗口本身也一样，它也是被
`build_as_child(&window)` 借走的。

## 平台专属的代码怎么在本地验

`cargo clippy --target x86_64-pc-windows-msvc` 在这台机器上跑不动整个 app
crate：`aws-lc-sys` 要编译 C 代码，缺 Windows 头文件（`windows.h`），
在 macOS 上补不了。core / tracker / installer 不受影响，能直接查。

app crate 里只有 UI 那部分是平台专属的。验它的办法是另起一个最小工程，只依赖
`wry` 和 `tao`，把出问题的那几行抄进去，用
`cargo check --target x86_64-pc-windows-msvc` 编一遍。借用关系对不对，编译器
会告诉你；真正的运行时行为还得靠 CI 的 windows runner 和真机。


## 安装器发现「已经装过」的时候，要问，不要失败

装过一次之后再跑安装程序是很平常的事（升级、换机器、装错了重装）。这时安装器
要做的不是报错退出，而是先问一句「要换成新的吗」。

判断「已经装过」靠的是「应用和功能」里的那条记录：它写着安装位置
（`InstallLocation`）和版本（`DisplayVersion`）。读这条记录比猜目录可靠。
但要注意记录可能比文件活得久 —— 文件夹没了就不算装过，要再确认一次目录在。

问的时候要把话说清楚：换掉的是程序文件，设置和命令行工具留着不动，正在运行的
SkycRemote 会被关掉。关掉它是有必要的：Windows 不让一个正在运行的程序的文件被
写覆盖，直接写会报「另一个程序正在使用此文件」。先 `taskkill` 再写才装得上。

换装的位置跟原来不一样时（比如原来只为你装，这次装成所有用户），旧的那一份
不要偷偷删掉 —— 把它的位置说出来，让人自己在「应用和功能」里卸。程序替人做
删除决定是危险的事。


## 设置归后端管，前端只管显示

以前页面把设置写进浏览器的 localStorage，程序自己的文件一次都没被写过 —— 那
个 `saveSettings` 命令从头到尾没人调用。于是设置存不住：WebView 的存储换了
地方就没了，重装程序更是不该影响它。

现在设置是后端的文件：`~/.config/skycremote/settings.json`（macOS），
`%APPDATA%\skycremote\settings.json`（Windows）。后端把窗口给的每一项都写
下去（包括它自己看不懂的那些），窗口启动时再读回来。后端存的是一个键值表，
不是一堆写死的字段 —— 窗口知道的设置比程序多，程序不该把不认识的丢掉。

写文件先写旁边的临时文件再改名，中途崩了也不会留下半个文件（半个文件读回来
等于没有设置）。

**码率的单位要统一。** 以前后端算的是千比特，页面算的是兆比特，同一个设置两
套单位。现在一律 Mbps，进到编码器之前再乘 1_000_000。旧的设置文件里那个
8000 是千比特，读进来要除以 1000 —— 不然会变成 8000 Mbps。

## 一件事只放在一个地方

Tracker 以前在共享面板里有一个输入框，设置里没有；控制端读的是设置里的那个
tracker，共享端读的是输入框里的那个。两边各填各的，改了哪边另一边不知道。

现在 tracker、设备 ID、显示名字都只住在「设置」里，共享面板只显示，不输入。
程序里也只有一处读它：`Settings::tracker()`。

**判据：一个设置只允许有一个输入框。** 出现第二个（哪怕是只读的）就该把这个
设置收回到一个地方，另一个地方只做显示。

## 共享中的参数要能改，还要说得清

共享开始时码率和帧率读一次就定死了，之后在设置里改完全没有反应 —— 用户只能
猜。改的做法是给共享服务留一个改参数的通道：`HostService::update_handle()`
给出句柄，改的时候把新的参数送进去，采集那边重新起一次（一帧的代价）。

光能改不够，还要说清楚哪些改了立刻生效、哪些要下次开始共享才算数（tracker
和设备 ID 属于一次会话）。后端在保存设置后回一句 `applied`，页面照着说。

## 日志留在程序里，不留在页面里

日志页面要能看程序做过什么，还要能清掉。日志本身是后端留着的（环形缓冲，
500 行），页面只是把它显示出来；关掉窗口再打开，日志还在。后端每做一件事
（开始共享、对面连进来、改了码率、命令失败）都往里写一行，页面通过
`log` 事件实时跟着长。


## 关窗口不是退出程序

共享开着的时候把窗口关掉，程序以前就跟着退了，共享也就断了。人要的是「窗口
关了，共享还在跑」。

现在关掉窗口只是把窗口收起来：

- macOS：`window.set_visible(false)`，同时把激活策略换成 Accessory，Dock 里
  那个图标就收起来了 —— 留着它是个陷阱，tao 没有 applicationShouldHandleReopen，
  点它什么也不会发生。换成菜单栏里的小闪电才是真的能点回来的。
- Windows：通知区里的图标。
- Linux：没有托盘图标，保留原来的行为（关窗口就退出）。托盘图标在 Linux 上要
  GTK，做不了就算了，别为了它把 Linux 的构建搞挂。

回来的路只有一条：托盘图标。所以托盘菜单里必须有「显示」和「退出」，窗口的
设置里也留一个「退出 SkycRemote」——不然程序就成了关不掉的。

**托盘图标必须在事件循环里建**，不能在 `run` 之前建：macOS 上它要求事件循环
已经在跑（tray-icon 的文档里就是这么说的）。图标本身是代码画的一个闪电（几个
点的多边形，扫描线判断在不在里面），不用带图片文件。

## tracker 要自己起来

以前 tracker 是个单独的命令，得另外开一个终端跑。两台机器都要用同一个 tracker
的时候还要有人在其中一台机器上一直开着它。

现在程序启动时看一眼设置里的 tracker 地址：

- 是本机地址（127.0.0.1 / localhost / ::1 / 0.0.0.0）而且端口上没人听 →
  自己起一个，记下局域网地址（对面那台要填的就是它）；
- 端口上已经有 tracker → 不重复起；
- 是别的机器 → 只记一行「那是别人的 tracker」，不多管闲事。

**127.0.0.1 只有本机能用**，所以对面那台机器填的必须是局域网地址。程序得把这个
地址说给用户听，否则两台机器就是连不上，而且看不出为什么。网卡地址用
`if-addrs` 拿（挑第一个私有 IPv4）。

设置里的 tracker 地址改了，本机的 tracker 也跟着换：老的停掉，新的按新地址
判断。

## tracker 也要说话

「为什么连不上」这个问题，光看共享那一头是看不出来的：tracker 可能根本没收到
登记，也可能收到了但对面不在线。所以 tracker 也要往日志里说话：谁登记了、
问了谁在哪、答案是不是在线。

tracker 是自己的库，不该知道窗口那边的日志长什么样，所以给它一个钩子：
`set_voice` 装一个回调进去，它每次做一件事就喊一声。窗口那边把回调接到日志
上。

## 日志写细不会把程序拖死

日志是环形缓冲，500 行，写满了从头开始丢。每写一行往窗口推一次。画面不在里面
——每一帧都走另一条通道（推给浏览器的解码器），要是把帧也写进日志，那才是
真的会死。

所以要写细的是「事情」：谁登记了、谁来了、参数改了、错在哪。不是「每一帧」。


## 口令和安全码：为什么是两样东西

访问口令是「谁可以连进来」，安全码是「连进来的是不是那台机器」。两件事不能互相
代替，所以分开做。

口令不写在设置文件里。文件里放的是口令散出来的值（PBKDF2，十万轮，加这台设备
自己的盐）。控制端输入口令后算出同一个值，两边用这个值做一份证明。证明里带着
两端的共享密钥，所以只有真正连到对端、并且知道口令的人才做得出来。设成设备的
盐每台机器都不一样，同一个口令在两台机器上的值不同，拿到其中一台的文件也不能
拿去开另一台。

安全码是会话密钥派生的六位数，两端显示的必须一样。不一样说明中间有人，这时这条
会话就不能用了 —— 口令只能挡住不认识的人，挡不住中间人。

口令错了要明确拒绝：被控端回一条「访问口令不对」然后断开，不给任何画面。控制
端也检查被控端的证明，口令不对时它自己就知道，不用等对方回答。

没有口令的机器默认不给控制。共享之前必须先在设置里填一个。这条不能商量：默认
放开就等于默认不安全。

## 加密放在哪一层

放在传输层，不放在协议层。理由是：协议消息和画面数据报是两条道，密文也得分别
处理。控制流每一帧前面多一个字节的标记，说明这一帧加没加密 —— 握手那几帧还没
有密钥，必须走明文，接收端靠这个标记才知道该怎么读。画面数据报整个加密，一个
数据报一个 nonce。

密钥在握手结束时才装到通道上，所以通道里的密文槽是共享的（`CipherSlot`），装
一次，所有副本都看得见。

一个密钥两个方向用是不行的：发出去的东西能被原样送回来。所以派生时按方向分成
四个密钥（控制两个方向、画面两个方向）。

## 界面重做：为什么把模式切换拿掉

以前是「控制 / 共享」两个模式来回切，连接以后又整页换成远程画面。用户反馈这套
逻辑绕，而且加东西（访问口令、安全码）只会更挤。

现在只有两个状态：列表页（上面「我的设备」，下面「远程设备」）和远程页（整屏
画面 + 底部工具条）。共享不再是模式，而是列表页上面那张卡片上的一个按钮。

连接别的机器要口令，所以点设备会弹一个输入框。填过的按设备记下来（存在后端的
`savedCodes` 里），下次直接连。

深色是默认的。远程控制多半在夜里用，深色省眼，看着也像正经工具。

## 文件传输的边界：只开放主目录

被控端让别人看文件、传文件，这条路一旦开大就等于把整台机器交出去。所以路径只
允许落在被控端用户的家目录以内，`..` 一律拒绝（`files::resolve` 里手工把路径
拆干净，不走 `canonicalize`，因为上传要写的文件还不存在）。

控制端下载到的文件放在自己的 `Downloads/SkycRemote` 里，不会散在各处。文件名
里的斜杠和别的怪字符被换掉，名字造不出越界的路径。

协议里的路径一律相对主目录。这样对面连家目录在哪都不用知道。

## 文件服务放在传输层外面

文件列表、文件下载这两件事写在 `core/src/transfer.rs` 里，不塞在 host 的会话
循环中。原因是会话循环没法单独测：它要一整个连接、一次握手，而且跑起来会碰屏
幕。拆出来以后，测试能拿一条真的 QUIC 连接调它，验证列目录、传文件、文件不在
时报错这几件事，一个字节都不能少。

测试用的文件夹放在家目录底下（`~/.skycremote-test-*`），因为家目录以外的地方
本来就应该被拒绝。测完自己删掉。

## 断线重连：谁重连

控制端重连。线断了不是有人按了挂断，所以连接自己再做一遍，最多十次，每次间隔
比上次长一点（免得对面的机器不在的时候被反复敲）。窗口上写明正在重连第几次，
重连成功写一行日志。

被控端不重连：它本来就在一直等着，谁来了都接待。

## 隐私屏：两个方向都有

对面（控制端）按隐私屏，是让被控端别再发画面过去。被控端自己按隐私屏，是旁边
有人经过时不想让人看见。两边都走同一条 `PrivacyScreen` 消息，所以对方那边会
知道画面为什么停了，不会以为是卡住了。

关掉的时机是「画面不再发出去」，不是「盖一层黑」—— 盖一层只是看着挡住了，底层
还在传。

## 电源操作：被控端执行

`shutdown` / `restart` / `sleep` / `logoff` 四个词过了线，由被控端自己执行
（macOS 用 osascript，Windows 用 shutdown 命令，Linux 用 systemctl）。控制端按
之前要问一遍，问的是「立刻」还是「等一下」，因为按下去之后会话会断。


## 开机自启：写进用户自己的地方

三个系统各有一套做法：macOS 是 ~/Library/LaunchAgents 里的 plist，Windows 是
启动文件夹里的快捷方式，Linux 是 ~/.config/autostart 里的 desktop 文件。

选的是「写在用户自己名下」这一类，不写系统目录、不装服务、不注册计划任务。代价
是它只在这台机器的这个用户下有用；好处是不用管理员密码。一个程序自己弹密码框
让人输管理员密码，是让人不敢再开它的最快办法。

macOS 的 plist 里 KeepAlive 是 false：程序崩了就崩了，不要系统一直把它拉起来。
Windows 的快捷方式用系统的 WScript.Shell 做，不是自己拼一个假快捷方式。

## 信任设备：为什么不能只是「少问一次口令」

控制端那边已经有「记住这台设备的口令」了：填过一次，之后直接连。这解决的是控制端
自己的麻烦，但它挡不住被控端——被控端每一台来连的机器都要重新问口令。

真正要的「信任设备」是被控端这一侧：这台电脑信任某台设备之后，那台设备连进来
不用再输口令。

做法是按长期公钥认人，不按口令认人：

- 控制端有一把自己的长期密钥（不是每次会话临时生成的那把），私钥只在这台机器上。
- 第一次连上，口令是照常问的。被控端验过口令以后，把控制端的长期公钥存下来，
  存的是「设备 id + 公钥」。
- 以后这台设备连来，控制端不出示口令，出示的是用长期私钥签的一份证明。被控端
  拿存下来的公钥验签，验得过就放行。

为什么不是「把口令记下来就免了」：那样被控端存的是能进这台电脑的凭据，存的地方
被读到就等于把口令送出去。存公钥不一样：公钥公开的，泄露了也只是让人知道「这把
钥匙是我的」，签不出东西。

为什么不是「按设备 id 放行」：设备 id 是自己报的，谁都能报同一个 id。按公钥才
是按钥匙本身认人。

这道改的是握手，所以单独放一个版本，不跟别的混在一起。
